How selection works

Applies to new runs

Your selection is saved immediately to data/settings.json, makes that provider active, and is used for every new run — no extra save step needed.

  • llama_cpp (llama.cpp): choosing a model restarts llama-server on the host via bash scripts/llamacpp.sh restart, then the new model is used immediately. Host-server knobs (llamacpp_ctx, llamacpp_model, host/port, n_gpu_layers) require that restart too.
  • ollama (Ollama): choosing a model tag is instant — Ollama switches per request and becomes the default provider.
  • openai (OpenAI-compatible): base URL, model and max tokens are configured in the Settings console; the API key is masked and never echoed back.
  • You can still override the provider and model per run in the Playground's selectors.
  • Per-runner configuration (URLs, model names, context sizes) lives in the Settings console: only the selected runner's settings are used. Other changes apply to the next run (or immediately, where labelled); Save as defaults also persists them.

Context window vs n_ctx

Shipped in Phase 4C

The agent prompt budget is default_context_window (default 8192). It is passed into the context builder: tool-schema tokens and a completion reserve are subtracted before history is added, so prompts fit the server context. The full 20-tool schema set is about 1.9k tokens; reducing enabled tools on the Tools page lowers per-step schema tokens.

The llama-server context is its n_ctx, set by CHEGE_LLAMACPP_CTX / llamacpp_ctx (default 8192). These are separate knobs: changing the server one requires bash scripts/llamacpp.sh restart. Other settings apply to the next run or immediately.

If a long thread still exceeds the prompt budget, start a new thread (or fork from a safe message) to shorten the history.
