How it works

From a prompt to verified changes in your workspace.

The short version: deploy with bash scripts/deploy.sh --isolated and open http://127.0.0.1:8001/. The browser talks to a versioned /api/v1/* REST API; the API starts an asynchronous run; the agent loop calls tools inside a sandboxed workspace; server-authored phases and structured activity stream back over SSE; you approve risky steps and inspect the diff.

The five-step lifecycle

Lifecycle

1 · Project

Use the New Project modal in the playground. It captures name, goal, stack and notes. A duplicate slug returns a clear 409 message, and creation is transactional so a partial failure leaves no orphan database or filesystem state. POST /api/v1/projects creates the workspace under workdir/ and a Git repository with an initial commit.

2 · Thread

A project has threads (sessions). Use the New Thread modal to give a thread a title, or the Fork modal to branch from an existing thread with up to N messages. The Context tab shows the inherited project goal, stack, notes, workspace path and todos (updated via POST /api/v1/sessions/{id}/todos). Threads share the project workspace, so concurrent runs can collide — avoid two edits in the same project at once.

3 · Run

POST /api/v1/runs returns 202 Accepted. Before any work begins, an automatic checkpoint snapshot is taken.

4 · Stream & approve

GET /api/v1/runs/{id}/events streams run.phase labels (for example "Preparing workspace", "Planning step N of M", "Waiting for the model"), token deltas, tool starts/results and approval requests. The playground shows a phase spinner while running, a separate Reasoning tab for thinking-capable models, and an Activity tab with ordered, escaped, redacted event summaries; task lists appear in the Context tab.

5 · Inspect & revert

Browse files in the Files tab's expandable tree, read the diff, commit, or POST /api/v1/runs/{id}/revert to return to the pre-run snapshot.

Approvals & tool governance

Approvals default to auto_edit: safe edits run automatically while destructive writes, shell commands and other risky actions ask first. You can select ask_all (confirm everything) or full_auto (skip risk-based prompts) per run, but tool governance always applies first — disabled tools and prompt_once grants hold even in full_auto. A checkpoint is taken automatically before every run.

The Tools page lists all 20 tools with a plain-language purpose, a technical description sent to the model, and a risk category (read / write / exec / network). You can disable a tool or set grant_mode to prompt_once, which asks for a user grant once per run before that tool executes; the grant is recorded and enforced.

Disabled tools are removed from the schemas sent to the model and blocked at execution time, so an injected tool-call cannot bypass the switch. Tool descriptions in the UI come from trusted server-side metadata.

Tool families

Files: read, write, edit, delete, list.

Execution: run commands, start/watch/stop background processes.

Git: status, diff, log, commit.

Search & web: grep, fetch, search.

Memory & planning: project brain, todos, ask-user.

On /tools you can search by name or description and filter by risk (Read / Write / Exec); the page shows an enabled count and summary. Fewer enabled tools also means fewer schema tokens.

Streaming events you will see

EventMeaning
run.startedThe agent loop accepted the run.
run.phaseServer-authored phase label with phase, label, step and max_steps — shown as the phase indicator.
message.deltaA chunk of the assistant reply.
thinking.deltaModel reasoning, shown in a collapsible accordion in its own chat bubble and in the Reasoning tab (thinking-capable models only). It expands while thinking and collapses when the answer starts.
tool.started / tool.output / tool.completedA tool was invoked and its (truncated) result returned.
tool.approval_requiredThe run is paused; approve or reject in the chat.
tool.ask_userThe agent asked a question; shown in the Activity feed.
todo.updatedThe task list changed; shown in the Context tab.
run.completed, run.failed, run.cancelledTerminal state; the stream closes.

Files tab: tree browsing

GET /api/v1/files/tree?project_slug=<slug>&max_depth=8&max_nodes=500 returns a nested {root, nodes, truncated, node_count} tree. Directories come before files, .git is ignored, and symlinks are shown but never traversed.

The Files tab renders a Linux tree-style expandable view with icons for folders, files and symlinks; even empty folders are visible. Depth (1–32) and node count (10–5000) are bounded, and truncated signals that a limit was hit. Opening a file keeps path containment and symlink-escape protection. The flat /api/v1/files, /api/v1/files/content and /api/v1/files/diff endpoints still work.

Tip: SSE replay honours the Last-Event-ID header (and ?after=), subscribes before replaying history and drops already-replayed live events, so a page refresh does not lose or duplicate output. Keep-alive pings arrive every 20s and the browser restores the active run view after a refresh. Raw server logs are not exposed; the Activity feed is built from structured, redacted summaries. Prompt injection is the main adversary in a local app with no login — read the safety model.
